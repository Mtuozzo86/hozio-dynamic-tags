== Version 4.17.0 (August 2026) ==

= New Features =

* Staging Index Guard. Catches staging sites that search engines are still
  allowed to crawl or index, and shows a non-dismissible banner in wp-admin AND
  on the front end with a one-click fix. A staging site is any site whose URL
  contains "mystagingwebsite.com" (filterable, plus a manual override).

  Two checks: "Discourage search engines" (the noindex tag, which is what
  actually keeps pages out of the index) and robots.txt. Because every staging
  site is a clone, robots.txt is normally a REAL file on disk copied from
  production - the web server serves it and WordPress cannot override it - so
  the fix writes the file, backs the old one up alongside it, and verifies the
  result by reading it back. It also flags a robots.txt whose "Sitemap:" line
  still points at the production domain.

  Two severity levels so the warning keeps its meaning: red when the site is
  genuinely indexable, orange when the noindex tag is protecting it but
  robots.txt is still permissive. A setting forces everything to red.

* Mirror guard for live sites. A PRODUCTION site set to "Discourage search
  engines" - almost always a staging database pushed to production - gets its
  own red banner. This is the more expensive version of the same mistake, and
  nothing else on the site reports it. Hozio Pro never changes this setting
  automatically on a live site; the banner links to the Reading settings.

* New "Search Engine Visibility" panel in Hozio Pro Settings: current status,
  Fix buttons, a "Re-check now" button that fetches the site's own robots.txt to
  show what the world actually sees, an on/off switch, an option to show the
  banner to logged-out visitors, and a manual environment override.

= Notes =

* Production safety: on a site that is neither staging nor mis-set to noindex,
  the guard registers no hooks at all - the only code that runs is the
  environment check and one autoloaded option read.

* No self-requests during page loads. The per-request check is local only (one
  option read plus one small file read, cached). The HTTP check runs on a button
  click or the daily cron, behind a lock and a cache, never on the front end.

* The banner renders on 'in_admin_header' at priority 1000 rather than as an
  admin notice, because Hozio Pro clears all admin notices at priority 999 on
  its own screens.

== Version 4.16.1 (August 2026) ==

= Fixes =

* Wrong-URL (ghost page) guard no longer blocks registered rewrite endpoints.
  The guard compared the raw request path to the page's permalink and treated any
  mismatch as a ghost URL, but URLs created with add_rewrite_endpoint() are
  legitimate sub-paths of a page and can never match the parent permalink. On
  WooCommerce sites this 301'd the whole My Account area back to the dashboard and
  killed the order-confirmation page: /my-account/orders/,
  /my-account/edit-account/, /my-account/edit-address/,
  /my-account/payment-methods/, /my-account/lost-password/ (so password resets),
  /my-account/view-order/123/, /checkout/order-received/123/ and
  /checkout/order-pay/123/. With the "WordPress Canonical Redirects" switch off the
  same URLs hard-404'd instead.

  The guard now reads the endpoints registered on WP_Rewrite and bails out when one
  is active on the request, so the fix also covers LearnDash, BuddyPress, EDD,
  membership plugins and custom endpoints - not just WooCommerce. Genuine ghost
  URLs (orphaned child pages at root-level URLs, mistyped slugs) are still blocked
  exactly as before.

= New Features =

* New "Block Pages at Wrong URLs" switch in Hozio Pro Settings, enabled by default.
  The guard previously could not be switched off at all - the only related setting,
  "WordPress Canonical Redirects", just chose whether it broke a URL via a 301 or
  via a 404. A single request can also be whitelisted in code with the new
  'hozio_skip_wrong_url_guard' filter.

== Version 4.16.0 (August 2026) ==

= New Features =

* Hub command "run_plugin_updates": the Hozio Hub can now trigger a site's normal
  plugin update run on demand instead of waiting for the twice-daily schedule.
  Refuses with a real reason when updates are blocked on the site or the
  Auto-Update All Plugins switch is off, rather than reporting "0 updated".
  Optional { max } tightens the per-run cap for that run only.

* Hub command "update_plugin": updates ONE named plugin and nothing else — for
  pushing a single security release across the fleet, or bringing one site back
  in line. Payload { plugin: "folder/file.php", force?: bool }.

  Guards: refuses Hozio Pro itself (use rollback_plugin, which carries the
  licence, version-lock and rollback-pause guards), refuses when updates are
  blocked, refuses plugins that are not installed, and refuses plugins managed by
  Git Updater. By default it still honours the site's exclusion list, the
  major-version guard, and the Auto-Update All Plugins switch; "force" overrides
  all three and is audit-logged as an override.

  Both commands reuse the same hardened run path as the settings-page button, so
  they inherit cron context (plugins are never silently deactivated mid-upgrade),
  the crash guard, stale-lock release and maintenance-mode handling.

= Fixes =

* Per-run update cap is now genuinely per RUN rather than per PHP request. A Hub
  heartbeat executes every queued command in one request, so a targeted update
  followed by a general update run previously shared one tally — the second run
  would refuse everything and report "0 updated" as though nothing needed doing.

* Hub patching commands now report failure honestly. Previously a run whose
  updates failed still returned success, so the Hub marked the site "completed"
  when the patch had not installed.

== Version 4.15.3(July 2026) ==

= Fixes =

* FOUND IT: "Run Plugin Updates Now" was deactivating the plugins it updated.
  Elementor was the one everybody noticed.

  This is a WordPress core behaviour, not an Elementor problem. Before replacing
  a plugin's files, core's Plugin_Upgrader silently deactivates it — and nothing
  in core ever switches it back on. Core deliberately skips that step during the
  scheduled background run, and its own comment explains why: "When in cron
  (background updates) don't deactivate the plugin, as we require a browser to
  reactivate it." The normal wp-admin update screens do that reactivation
  themselves. Our button ran as an AJAX request, which is neither of those, so
  core deactivated each plugin and no one turned it back on.

  The manual run now declares cron context for its duration, putting it on the
  exact code path the twice-daily run uses — the path this button always claimed
  to be. Core no longer deactivates anything, and it also manages maintenance
  mode around the file swap properly.

  This only ever affected the button. The twice-daily automatic run was never
  affected, because it genuinely is cron.

* Added a safety net regardless: the active plugins are recorded before a run,
  and anything switched off during it is switched back on — including when the
  run is killed by a timeout, which could previously leave a plugin deactivated
  with its files already swapped. Reactivation is silent, is skipped if the
  plugin's files are missing, and cannot resurrect a plugin that WordPress has
  paused for crashing (core uses a separate mechanism for that). Every
  reactivation is named in the audit log.

= Compatibility =

* Git Updater is now respected. On a site running Git Updater (or the older
  GitHub Updater), any plugin declaring a GitHub / GitLab / Bitbucket / Gitea /
  Gist URI is left alone — two updaters writing the same plugin folder is how a
  plugin ends up half-installed, and Git Updater is frequently tracking a branch
  rather than a release, so installing "the newest version" over it can discard
  exactly what the site is meant to run.

  Only the plugins Git Updater manages are skipped; everything else on the site
  is still patched. Skips are named in the audit log, the settings page explains
  the situation when Git Updater is detected, and the Hub heartbeat reports it so
  those plugins are not counted as permanently behind.

  Git Updater is never deactivated automatically. Switching off a plugin the site
  owner deliberately installed — mid-request, while its hooks are loaded — risks
  a fatal, breaks their intended workflow, and would leave the site with it off
  if the run then failed.

* Hozio Pro no longer declares a "GitHub Plugin URI" header. Nothing here read
  it; its only consumer was Git Updater, which would claim Hozio Pro and update
  it from the main branch, bypassing the licence check, version lock and
  post-rollback pause that our own updater enforces.

== Version 4.15.2 (July 2026) ==

= Fixes =

* A site could be left stuck on "Briefly unavailable for scheduled maintenance"
  after running plugin updates. Fixed, in two parts.

  What happened: WordPress puts the site into maintenance mode (a .maintenance
  file in the web root) while it installs an update, and removes it when done. On
  shared hosting, PHP requests are capped by max_execution_time and many hosts
  ignore set_time_limit(), so a run that tried to install several plugins was
  killed partway through — leaving that file behind. The site then served the
  maintenance page to every visitor until core expired the file ten minutes
  later, and the stranded updater lock blocked further attempts for an hour.

  1. "Run Plugin Updates Now" installs ONE plugin per request and the browser
     asks for the next one, repeating until the backlog is clear. A single
     update finishes well inside any host's limit, and a request that is killed
     can now only cost one plugin instead of the whole batch. Keep the settings
     page open while it works; progress is shown as it goes.

  2. A crash guard now runs on both the button and the twice-daily automatic run.
     It fires even on a timeout or fatal error, deletes the .maintenance file,
     releases the updater lock, and writes what happened to the audit log. The
     site comes straight back online instead of waiting out the ten minutes, and
     the next run is not blocked. This matters most for the unattended run, where
     nobody is watching to notice the site went down.

* The manual button no longer attempts core, theme, or translation updates. It
  says plugins, so it does plugins — and a core update is a large download that
  made a timeout considerably more likely. The automatic run is unchanged.

== Version 4.15.1 (July 2026) ==

= Fixes =

* "Run Plugin Updates Now" now clears a stale auto-updater lock before running.

  WordPress guards automatic updates with a lock (auto_updater.lock) that is only
  released at the end of a successful run. Any run that timed out, fatalled, or
  was interrupted leaves it stranded for a full hour — and while it is held,
  WP_Automatic_Updater::run() returns SILENTLY. No error, no results, nothing
  logged. Every click during that hour appeared to do nothing, which is what made
  "13 update(s) are pending but none installed" so hard to explain.

  The manual button now releases the lock first: the operator is explicitly
  asking for a run. The scheduled cron path still honours the lock, which is what
  prevents concurrent runs.

* The "pending but none installed" message now breaks the number down — how many
  are major-version updates (skipped by design), how many are excluded, and how
  many were genuinely eligible — so it is clear whether the cause is this
  plugin's own policy or something in WordPress/the environment.

== Version 4.15.0 (July 2026) ==

= New Features =

* "Override and force updates on": a new opt-in setting that re-enables
  WordPress's automatic updater on sites where something has switched it off.
  Update-management plugins (ManageWP Worker, MainWP Child), security plugins,
  the AUTOMATIC_UPDATER_DISABLED constant, and some host mu-plugins all disable
  it — which silently prevents any plugin from installing unattended.

  OFF by default and deliberately opt-in: if a tool is genuinely managing
  updates, forcing WordPress to update as well means two systems writing the
  same plugin directories. Enable it only when the settings page reports that
  automatic updates are switched off.

  It cannot override a host-level lock (DISALLOW_FILE_MODS) or missing direct
  write access — WordPress checks those before the filter, and they mean writes
  genuinely are not permitted. Those are still reported separately.

* Update schedule self-heal: if the wp_maybe_auto_update cron event has been
  removed (the "next automatic run: not scheduled" symptom), Hozio Pro restores
  it. Without that event nothing can ever install unattended, regardless of any
  other setting. This runs whenever Auto-Update All Plugins is enabled.

== Version 4.14.2 (July 2026) ==

= Fixes =

* "Run Plugin Updates Now" no longer reports "all plugins are already current"
  when updates are actually pending. When WordPress's automatic updater is
  disabled it returns silently without firing its completion hook, which the
  button previously read as "nothing to do" — the most misleading possible
  outcome. It now reports the real reason instead:

    - WordPress automatic updates are switched off (an update-management plugin
      such as ManageWP Worker or MainWP Child, a security plugin, the
      AUTOMATIC_UPDATER_DISABLED constant, or a host mu-plugin). The
      "next automatic run: not scheduled" note is the same symptom.
    - File modifications are disabled (DISALLOW_FILE_MODS).
    - The site is under version control (.git / .svn present).
    - WordPress cannot write to the plugins directory directly.

  If updates are pending but none installed, it now says so explicitly rather
  than claiming the site is current — that case usually means the pending
  updates are all major versions, which 4.14.1 skips by design.

* The blocking reason is also sent to Hozio Hub in the heartbeat, so a site that
  physically cannot update is visible fleet-wide instead of appearing healthy.

== Version 4.14.1 (July 2026) ==

= Fixes =

* Auto-updates no longer install MAJOR version jumps (e.g. 3.x -> 4.x). Major
  releases carry breaking changes, and the sharpest case is a free plugin whose
  premium counterpart cannot follow: Elementor updating 3.x -> 4.x while
  Elementor Pro (no license = no update offered) stays on 3.x. Pro then fails its
  compatibility check, causes a fatal error, and WordPress deactivates it.

  Security fixes ship in patch and minor releases, so declining majors keeps the
  patching benefit while removing this failure mode. Major updates still appear
  in wp-admin as normal and can be installed by hand, alongside any paid add-on.

  Skipped majors are recorded in the audit log. Override with the
  hozio_block_major_auto_updates filter if a specific site needs them.

== Version 4.14.0 (July 2026) ==

= New Features =

* Auto-Update All Plugins: WordPress can now automatically install updates for
  every plugin on the site, not just Hozio Pro. This uses WordPress's own
  auto-update system — it already checks for plugin updates twice a day; this
  grants permission to install what it finds. On WordPress 6.3+ WordPress
  automatically restores the previous version if an update causes a fatal error.

  ENABLED BY DEFAULT. Turn it off per-site in Hozio Pro Settings -> Feature
  Toggles, or remotely on Hub-connected sites via the update_option command
  (hozio_auto_update_all_plugins = '0').

* Exclusion list: plugins listed in Hozio Pro Settings are never auto-updated.
  Use this for premium or heavily customized plugins you want to update by hand.
  Accepts either the folder name (elementor-pro) or the full plugin file
  (elementor-pro/elementor-pro.php).

* Per-run cap: a maximum of 3 plugins are updated per run, so a site with a
  large backlog works through it over several runs rather than attempting
  everything in one request (which risks a PHP timeout mid-update). Steady-state
  sites are unaffected. Filterable via hozio_max_plugin_auto_updates_per_run.

* "Run Plugin Updates Now" button: runs the same process the twice-daily cron
  runs, immediately, and reports what was updated. No WP-CLI required. The
  settings page also shows when the next automatic run is due.

* Every automatic plugin update — success or failure — is written to the audit
  log (wp-content/hozio-audit.log) under the AutoUpdate context.

= Notes =

* Hozio Pro is deliberately excluded from this setting; it continues to update
  through its own updater, which carries additional guards (valid license,
  version lock, post-rollback pause).

* Premium plugins without an active license are skipped automatically, because
  no update is offered for them. Those still require manual updating.

== Version 4.12.5 (May 2026) ==

= Improvements =

* Improvement: Consolidated all HTML output fixes into a single unified output
  buffer (ob_start at priority 0). Previously the cta-text-color deduplication
  ran in its own buffer at priority 10; it now shares one pass with the new
  universal fixer, reducing overhead on every front-end page load.

* New: Universal HTML Validation Fixer — four server-side fixes applied to
  front-end HTML before delivery:
    A. Duplicate id="cta-text-color" deduplication (existing, now merged in)
    B. Inline <script> CDATA wrapping — validators that check XHTML rules flag
       bare & / < / > in JS blocks; wrapping with //<![CDATA[ ... //]]> silences
       this. JSON-LD (application/ld+json) and non-JS script types are explicitly
       excluded to protect structured data.
    C. Nav menu <ul>/<li> line normalisation — Elementor concatenates list items
       onto one line; validators lose the parent <ul> context. Newlines restore
       correct nesting visibility.
    D. Elementor lightbox attribute entity cleanup — captions with special
       characters get double-encoded (&quot; etc.) inside data-elementor-lightbox-
       title / -description attributes. Decoded and re-encoded cleanly.
  All fixes are gated on fast strpos() checks so pages without the pattern are
  untouched. Skipped on admin, AJAX, REST, WP-CLI, and feed requests.

== Version 4.12.3 (May 2026) ==

= New Features =

* NEW: Search-replace protection for all Hozio Pro settings — every editable
  field on the Dynamic Tags Settings page is stored base64-encoded in

  mangle them. Reads are decoded transparently — Elementor dynamic tags,
  shortcodes, admin display, and any get_option() consumer always see plain
  text. Protected fields: phones, emails, address parts, business hours
  (HTML and Classic structures), URLs, colors, and custom dynamic tags.
  One-time auto-migration encodes existing plain-text values on first
  admin page load.

* NEW: Email validation on Contact Form Email(s) — rejects malformed
  addresses on save with a prominent red banner pointing at the bad
  values. Comma-separated lists (e.g. "support@hozio.com, sales@hozio.com")
  remain valid. Client-side check on submit blocks bad input instantly;
  server-side check is a safety net.

= Trade-off =

* Domain migrations that update URLs via search/replace will NOT update
  URLs stored in the protected fields. After such a migration, re-save the
  Dynamic Tags Settings page once.
